## 0. 一句话结论

1. **你参考的 [abdullahtarek/football_analysis](https://github.com/abdullahtarek/football_analysis) 只能当读物，不能当地基。** 它的流水线概念是对的（检测→跟踪→分队→球权→坐标变换→速度距离），但实现处处硬编码到某个具体机位：4 个单应性源点是写死的像素、fps 写死 24、球不做跟踪、无身份保持、**仓库无 LICENSE**（默认保留所有权利，商用不可用）。
2. **没有任何开源项目能直接变成平台。** 现成的只有"零件"：`roboflow/sports`（MIT，标定+分队+小地图）、`torchreid/OSNet`（MIT，ReID 特征）、`sn-trackeval`（MIT，跟踪评测）。**事件层、身份层、数据层、服务层是公开的空白**——这既是你的工作量，也是你的价值所在。
3. **你这台没有独显的机器，离线分析完全够用**（实测见第 2 节）：整场 90 分钟 1080p 逐帧处理约 **3.8 小时**；每 3 帧抽 1 帧处理约 **1.1 小时**；检测若改走 **ONNX Runtime DirectML（核显）**，单帧从 26.7 ms 降到 **11.8 ms（快 2.3×）**。实时是另一回事，先别想。
4. **头号技术风险不是"检测不到人"，而是"同一人前后不是同一个 ID"。** 实测 300 帧（10 秒）广播片段里，平均每帧只有 14.5 个目标，却出现了 **93 个不同 track id**。学术侧结论一致：GSR 挑战的瓶颈在关联不在检测（2025 冠军 GS-DetA 51.36 vs GS-AssA 79.55）。跑动距离一旦跨 ID 累加就会错得离谱。
5. **许可红线要先定**：`ultralytics`（YOLOv8/YOLO11）是 **AGPL-3.0**，`boxmot` 是 **AGPL-3.0**，`sn-gamestate`/`sportslabkit` 是 **GPL-3.0**。如果你的平台要闭源商用，这三条都绕不开（见第 4 节）。

### 1.1 abdullahtarek 版的具体硬伤（换场景必坏）

| 位置 | 症状 | 后果 |
|---|---|---|
| `view_transformer/view_transformer.py:9-12` | 单应性源点写死 `[[110,1035],[265,275],[910,260],[1640,915]]` | **换机位/换分辨率直接废掉**；目标尺寸 `23.32 m` 只是该取景框可见的那一段，不是标准场地 |
| `speed_and_distance_estimator.py:9`、`utils/video_utils.py:15` | `frame_rate = 24` 写死 | 速度整体错 25%（30fps 素材）；输出视频帧率也错 |
| `camera_movement_estimator.py:20-22` | 光流特征点 mask 写死 `x∈[0,20)∪[900,1050)` | 针对某个 1920×1080 机位手调 |
| 同上 `:56`、`:61-72` | 取**最大位移**当全局平移（非中位数/RANSAC）、丢弃 `status`、`old_features` 与 `old_gray` 更新不同步 | 单个 outlier 污染整帧；慢速平移段光流必然不收敛 |
| `trackers/tracker.py:93-98` | **球不做跟踪**，每帧硬写 `{1: ...}` | 同帧多球检测互相覆盖，球轨迹不可用 |
| `team_assigner/team_assigner.py:68-69` | `if player_id == 91: team_id = 1` | 针对特定视频的手工补丁 |
| `main.py:46-47` + `team_assigner.py:60-61` | 只用**第 0 帧**校准分队，且每个 ID 只判一次并永久缓存 | 光照变化/换人即错 |
| `player_ball_assigner.py:7` | 球权阈值 `70 px`（像素，非米） | 与分辨率死绑 |
| `utils/video_utils.py:3-11` | 把**整段视频所有帧读进内存** | 750 帧≈4.6 GB；整场 16.2 万帧 ≈ **1 TB，必然 OOM** |
| 全仓 | 无 ReID、无换人、无球出界、无多机位 | 长期统计不可信 |

**结论**：可复用的是两个**思路**（"球到脚的最近距离"度量、"上半身+四角像素投票"定球衣底色）；代码基本要重写。

### 1.2 进化版（songminkyu）做对了什么 —— 值得抄的升级

1. **单应性不再硬编码**：每帧用 32 点球场关键点模型实时求 `findHomography`，并对 3×3 矩阵做指数平滑（`alpha=0.9`）→ **换机位仍可用**。这是最关键的结构性升级。
2. **不需要相机运动补偿**：既然每帧重估单应性，镜头动 H 就跟着动，比"光流平移"高一个档次。
3. **球权判定达到可用水平**（`ball_to_player_assignment/`）：投影到场地坐标后算距离 + **点球点屏蔽**（防把点球点误认成球）+ **球速校验**（跳变过大判误检）+ **双 grace period**（4 s 保留上一持球人 / 2 s 容忍球消失）。**建议整段移植**，但要修两个 bug：fps 未注入（默认 30）、点球点索引写错（传了 24 号关键点，那是角旗区）。
4. **三线程流水线**（Capture/Processing/Display + 队列）比参考版的全内存读法正确。

**它的硬伤**：x/y 两轴像素→米换算比例不一致（y 向速度系统性偏约 25%）；每帧全量重写 JSON（O(n²)）；权重需自训（`models/weights/` 被 gitignore）；`os._exit(0)` 强杀进程。

## 2. 本机实测：这台没有独显的机器到底能不能用

**能，而且比预期好。** 全部数据是在你这台机器上现场跑的（脚本 `scripts/bench_cpu.py`、`scripts/bench_pipeline.py`，原始数据 `docs/bench/`）。

### 2.1 检测速度（1080p 输入，真实比赛画面）

| 后端 / 模型 | imgsz | ms/帧 | FPS |
|---|---|---|---|
| YOLOv8n · PyTorch CPU | 640 | **26.7** | 37.5 |
| YOLOv8n · PyTorch CPU | 960 | 48.5 | 20.6 |
| YOLOv8n · PyTorch CPU | 1280 | 79.4 | 12.6 |
| YOLO11n · PyTorch CPU | 640 | 28.7 | 34.9 |
| YOLO11n · PyTorch CPU | 1280 | 133.7 | 7.5 |
| **YOLOv8n · ONNX Runtime DirectML（780M 核显）** | 640 | **11.8** | **84.9** |
| YOLOv8n · ONNX Runtime CPU | 640 | 57.2 | 17.5 |

> **核显不是摆设**：`onnxruntime-directml` 能直接用上 Radeon 780M，**比 PyTorch CPU 快 2.3 倍**。但注意：**这批开源项目没有一个支持 DirectML**（`boxmot` 的设备白名单只有 `cpu/mps/cuda`，显式传 cuda 还会直接抛异常），要用核显必须自己写 ONNX 推理层。
> 另注：上表的 ONNX-CPU 比 PyTorch-CPU 慢，是 ORT CPU EP 的线程配置没调优所致，不代表 ONNX 本身慢。

### 2.2 其它开销（这些往往被忽略）

| 步骤 | ms/帧 | FPS | 说明 |
|---|---|---|---|
| 稀疏光流（Shi-Tomasi + LK） | **60.7** | 16.5 | **比检测还贵 2 倍**。固定机位根本不需要它 → 自建摄像头直接省掉 |
| 稠密光流（Farneback） | 555.7 | 1.8 | 不要碰 |

### 2.3 端到端真实吞吐（检测 + ByteTrack + 视频解码 + 绘制）

| 配置 | 处理帧数 | 耗时 | 相对实时 | **整场 90 min 预计** |
|---|---|---|---|---|
| YOLOv8n@640，逐帧 | 300 | 25.1 s | 0.40× | **3.8 小时** |
| YOLOv8n@640，每 3 帧抽 1 帧 | 150（=450 源帧） | 11.4 s | 1.32× | **1.1 小时** |

**ID 碎片化的现场证据**：逐帧那一次，300 帧里平均每帧 14.5 个目标框，却累计出现了 **93 个 track id**。
（该样例含镜头切换与摇摄，不能当严谨的 HOTA 评测，但它直观说明了 ByteTrack 默认参数在足球场景下有多碎。）

### 2.4 结论
- **离线批处理：你这台机器够用。** 一场比赛晚上挂着跑，第二天早上出报告。
- **实时：不够，也别做。** 端到端 12 FPS 追不上 30 fps 源。真要做实时，必须上独显或 Jetson。
- **优化优先级**：① 检测走 DirectML（−56% 时间）② 死球/远景段抽帧（vid_stride）③ 去掉光流补偿（固定机位）④ 分队/ReID 只在稀疏关键帧上跑，不要逐帧。

## 3. 开源全景：按"平台需要的能力"分层看

你的三个目标分解成六层能力，逐层看开源能给什么：

### 第 1 层 · 检测（球员 / 球 / 裁判 / 门将）
- **可用**：`ultralytics`（YOLOv8/YOLO11）+ 足球专用权重。Roboflow Universe 有现成数据集/模型：`football-players-detection-3zvbc`、`football-ball-detection`、`football-field-detection`——`roboflow/sports` 的 `examples/soccer/notebooks/train_{player_detector,pitch_keypoint_detector,ball_detector}.ipynb` 就是教你在这三个数据集上微调。
- **坑**：球是小目标。`roboflow/sports` 的做法是**切片推理**（`sv.InferenceSlicer(slice_wh=(640,640))` + `nms 0.1`），球单独用一个检测器、球员用另一个——别指望一个模型同时搞定。
- **许可**：数据集许可逐个看（Roboflow Universe 上有的是 CC BY 4.0，有的是非商业）；`ultralytics` 代码是 AGPL-3.0（见第 4 节）。

### 第 2 层 · 跟踪（跨帧身份）
- **可用**：`supervision` 的 `ByteTrack`（最省事，`roboflow/sports` 就用它）；要更强就 OC-SORT / BoT-SORT / Deep-EIoU。
- **现实**：`boxmot`（15+ 跟踪器 + ReID，唯一生产级底座）是 **AGPL-3.0**；`sportslabkit` 的 `SORT/DeepSORT/TeamTracker` 是 **GPL-3.0** 且 2023-12 已停更。
- **学术结论**：足球场景下卡尔曼线性运动假设会翻车——SportsMOT 论文自证 ByteTrack 去掉运动预测反而 **+7.4 HOTA**。选型时不要默认"卡尔曼一定更好"。

### 第 3 层 · 标定（画面 → 球场米制坐标）★最关键的一层
- **固定自建机位的最优解**：手工点 8–12 个可见球场关键点 → `cv2.findHomography`。只要你会标一次，这一步就解决了，**不需要任何模型**。
- **`roboflow/sports`（MIT）给了现成零件**，可直接照抄：
  - `sports/configs/soccer.py` → `SoccerPitchConfiguration`：标准球场 32 个顶点的**厘米**坐标（`7000 × 12000`）
  - `sports/common/view.py` → `ViewTransformer(source, target)`：21 行封装 `findHomography`，`transform_points()` 出球场坐标
- **自动标定（可选）**：`PnLCalib`（关键点+线联合优化，GPL-2.0）当**离线工具**跑一次出 H；`tvcalib`（MIT）作为算法参考。两者都只在转播数据上训练过，域外精度未验证。
- **⚠️ 单位陷阱**：`roboflow/sports` 用**厘米**（12000×7000），`sportslabkit` 用**米**（105×68）。混用必然出错，本项目统一用**米**。

### 第 4 层 · 球队区分
- **可用**：`roboflow/sports` 的 `TeamClassifier`（`sports/common/team.py`）= **SigLIP 提特征 → UMAP 降到 3 维 → KMeans 2 簇**。权重 `google/siglip-base-patch16-224` 从 HuggingFace 自动下载，不需要任何 API key。**MIT 许可，这是全链条里最干净的一环。**
- **三个必须处理的坑**：① 官方示例是**稀疏采样帧上 `fit()`、再逐帧 `predict()`**，而 `Smasko7/Football-Vision` 漏了 `fit()` 导致开箱即崩；② UMAP+KMeans **不落盘**，每次运行都要重算 → 应改成"首次拟合后保存，后续加载"；③ 门将不参与聚类，用"离哪队质心近"单独归属。
- 简化替代（画质差时更稳）：HSV 去掉草地绿 → 取上半身主色 → 与两队锚色比最近。`songminkyu` 版就是这么做的，代价是队服色要人工填一次。

### 第 5 层 · 身份保持 / 长期 ReID ★开源的最大空白
- 学术现状：跨机位 ReID **近乎饱和**（SoccerNet 2023 冠军 CLIP-ReIdent 93.26 mAP），但那是转播画质；**自有摄像头下号码区只有几十像素，读不出**（号码识别研究用 512 px 的号码图才到 92%）。
- 可用的干净零件：`deep-person-reid`（torchreid / OSNet，**MIT**）——几行拿到 embedding，配自写匈牙利匹配即可。注意 OSNet 是行人域（MSMT17）预训练，球场跨域有落差。
- **务实策略（强烈建议照做）**：不要追求全自动身份。优先级为
  `彩色背心/大号高对比号码` > `时空约束（速度上限、队伍分区、同帧唯一）` > `自动跟踪 + 关键节点人工确认一次` > `外观 ReID（只作辅助证据）`。
  学术侧佐证：GSR 2024 基线 GS-HOTA 仅 22.26%，2025 基线 29.01%、**冠军 63.90** —— 两年几乎原地踏步。

### 第 6 层 · 统计与事件层 ★开源几乎为零
- **能从轨迹直接算**（建议先做）：**总跑动距离**、速度剖面、**控球时间占比**、pitch control / Voronoi 空间控制、位置热图、阵型轮廓。
- **必须有事件层**：传球次数、传球成功率、xG/xT/VAEP、PPDA。
- **精度预期（要写进产品说明）**：专业多相机系统 vs VICON 参考，总距离误差仅 0.42±0.60%，但**低速段距离偏差 −19.41±13.24%**、高速段 +8.94±9.49%（Linke et al., PLOS ONE 2020）。单目/鱼眼远远达不到这个水平——**低速区间的距离数据本质不可信，必须显式标注**。
- 详见 `docs/11-从轨迹到统计指标.md`（滤波选型、控球判定、传球检测、口径差异、实现优先级）。

### 第 7 层 · 平台外壳（DB / API / 前端 / 任务调度）
**公开空白。** 调研了 20+ 个仓库，没有发现任何一个把"数据库 + API + 前端报表 + 任务队列"做起来的足球分析平台。最接近生产的是 `sn-gamestate`（GPL-3.0，绑定 Hydra+tracklab，只认 SoccerNet 转播数据，Windows 上装不动），它也只是**研究基线**不是服务。

**给平台化的三条硬结论**：
1. 想闭源，检测器就不能用 ultralytics 的实现 → 换 **RT-DETR（Apache-2.0）** 或 YOLOX，用 ONNX 自己写推理层（顺带能吃下核显 DirectML 的 2.3× 加速）。
2. 跟踪不要依赖 `boxmot` → 按 BoT-SORT/OC-SORT 论文自写关联（CMC 部分就是几十行 OpenCV），ReID 特征用 MIT 的 torchreid。
3. 干净组合：**`roboflow/sports`(MIT 零件) + `torchreid`(MIT 特征) + `sn-trackeval`(MIT 评测) + 自写跟踪/事件/数据层**。

## 5. 学术 SOTA 现状（决定"哪些值得抄"）

| 方向 | 现状 | 对你的意义 |
|---|---|---|
| 足球 MOT | SportsMOT HOTA：ByteTrack 62.8 / BoT-SORT 68.7 / OC-SORT 71.9 / **Deep-EIoU 75.3** | 换个关联器就能涨 10+ 点，**性价比最高的一步** |
| 固定鱼眼全景 | SoccerTrack Challenge 2025 冠军 GTATrack（Deep-EIoU + 全局 tracklet 关联）HOTA 0.60 | 这是**唯一**和你"自建固定机位"同赛道的赛道 |
| Game State Reconstruction | 200 段×30 s，GS-HOTA = 定位相似度 × 身份相似度；2024 冠军 63.81、2025 冠军 63.90（基线 29.01） | 两年停滞 = 说明这件事**真的难**，别信"跑个开源就全对" |
| 标定 | 2023 冠军 Score 0.5535 / Acc@5 0.7322 | 转播多机位都只能到这个水平，固定机位反而简单 |
| 事件 spotting | 2022 tight mAP 67.81（转播视频、单时间戳） | **对你的场景适用性低**：它绑定了转播语言（回放、字幕板、导播切换），且只给时间戳不给"谁传给谁" |
| 球与出界 | 纯视觉无公认基准；工业界走球内传感器 | 别指望开源方案能判出界 |

**唯一公开的"固定机位 + 米制真值"数据集**：[SoccerTrack v2](https://atomscott.github.io/SoccerTrack-v2/)（10 场、932 分钟、4K 固定全景、逐帧米制坐标 + 号码 + 身份 + 角色 + 球队 + 12 类球事件）。**这是你做自有摄像头系统最该对标的基准。**

## 6. 不要做的事

- ❌ 不要把 `abdullahtarek/football_analysis` 的代码抄进产品（无 LICENSE + 处处硬编码）。
- ❌ 不要指望单机位 4K 能读球衣号码（远端仅 20–30 px，号码识别需要 50–100 px 级）。
- ❌ 不要用 30 fps 追球（球速 30 m/s，每帧位移约 1 m，而球直径只有 0.22 m）。
- ❌ 不要用针孔模型直接标 180° 鱼眼画面（必须先用鱼眼模型去畸变）。
- ❌ 不要追求全自动身份，也不要让 ReID 进实时链路。
- ❌ 不要把 `sn-gamestate` 当起点（GPL-3.0 + torch 1.13 + mmcv 编译 + Python 3.9 + GB 级转播数据，Windows 上跑不动）。
- ❌ 不要相信"传个视频进去就出专业数据"的演示——GSR 挑战两年冠军才 63.9 GS-HOTA。
