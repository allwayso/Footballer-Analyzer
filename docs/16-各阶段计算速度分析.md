# 各阶段计算速度分析

## 1. 测试口径

本机为 AMD Ryzen 7 8745H、Radeon 780M 核显、约 20 GB 内存，当前应用使用 CPU 推理（6 个 PyTorch 线程），系统为 Windows 11。下面的“实测”来自 `outputs/run_*/manifest.json`、逐帧白线标定的 `summary.json` 和足球结果的 `manifest.json`；早期模型对照来自 [02 本机实测数据](02-本机实测数据.md) 与 [15 球检测模型对照与跨帧筛选](15-球检测模型对照与跨帧筛选.md)。

吞吐统一按：

```text
处理 FPS = 处理源帧数 / 墙上耗时
每帧耗时 = 墙上耗时 / 处理源帧数
```

相对实时速度还取决于源视频帧率。当前素材主要是 25 FPS，也有 30 FPS 素材；`1.0×` 表示处理速度与源视频播放速度相同。所有数字都是本机离线处理结果，受首次加载、磁盘写入、后台负载和热降频影响，不能直接当成其他设备的承诺。

## 2. 结论先看

| 环节 | 当前实现的典型吞吐 | 主要成本 | 结论 |
|---|---:|---|---|
| 人物追踪，`imgsz=1920` | 约 4.9–5.5 FPS（183–205 ms/帧） | 人物检测、ByteTrack、检测与轨迹产物写盘 | 当前最重的基础阶段之一；精度版明显慢于 1280 |
| 场地逐帧白线标定 | 约 5–9 FPS（110–200 ms/帧） | 白线提取、候选单应性、连续优化、掩膜 PNG 写盘 | 与人物追踪同量级；长片耗时会明显累积 |
| 场地手动固定标定 | 没有逐帧耗时 | 一次 `findHomography`、几何校验和浏览器预览 | 计算成本很小，主要耗时在人工点选和回看；只需做一次 |
| 足球追踪，默认 640 切片 | 约 2.3 FPS（约 436 ms/帧） | 每帧多块切片 YOLO 推理、去重、时序束搜索、JSON 写盘 | 当前最慢；小目标收益换来约 20 倍实时处理时间 |
| 足球追踪，全图 1280 对照 | 约 10.6–13.9 FPS（72–94 ms/帧，检测基准） | 单次全图 YOLO 推理 | 比切片快约 3–4 倍，但远端小球漏检风险更高 |

因此，当前 CPU 版本的典型速度排序是：**手动固定标定最快，人物追踪与逐帧白线标定居中，足球切片追踪最慢**。足球结果必须单独运行，不能把足球切片的耗时误认为人物或场地阶段的耗时。

## 3. 人物追踪

人物阶段的 `manifest.elapsed_s` 包含视频检查、模型初始化、球衣颜色预采样、人物检测、ByteTrack 关联和产物写盘，不包含 Python 进程启动导入。相同素材的短窗口存在启动开销，因此长窗口更能代表持续吞吐。

| 配置 | 实际帧数 | 墙上耗时 | 吞吐 | 每帧耗时 |
|---|---:|---:|---:|---:|
| YOLO 人物，`imgsz=640` | 125 | 10.0–10.7 s | 11.7–12.5 FPS | 80–86 ms |
| YOLO 人物，`imgsz=1280` | 125 | 16.9–17.2 s | 7.2–7.4 FPS | 136–138 ms |
| YOLO 人物，`imgsz=1920` | 377 | 69.3–76.5 s | 4.9–5.4 FPS | 184–203 ms |
| YOLO 人物，`imgsz=1920` | 1503 | 275.2–308.0 s | 4.9–5.5 FPS | 183–205 ms |

用 1920 精度版的长片吞吐约 5.2 FPS 粗略外推，25 FPS 的 90 分钟视频约需 7.2 小时，30 FPS 约需 8.7 小时。这个外推只适用于当前 CPU、输入尺寸和代码路径；不能从短片的 8 帧运行推断长片速度。

输入尺寸对速度影响很大：从 640 提高到 1280，实际人物运行约慢 1.6 倍；提高到 1920 后约为 1280 的 1.4 倍。1920 主要用于当前的精度复核，不适合在 CPU 上追求准实时。

## 4. 场地标定

### 4.1 逐帧白线标定

逐帧标定由 `white_line_pipeline.py` 调用 `WhiteLineCalibrator.process`，每帧都重新提取白线，并使用上一帧先验、候选几何、鲁棒优化和质量检查；同时保存透明白线掩膜。因此它不是一次单应性计算，而是完整的视频阶段。

已保存运行的范围如下：

| 运行长度 | 墙上耗时 | 吞吐 | 备注 |
|---|---:|---:|---|
| 125 帧 | 14.4–16.2 s | 7.7–8.7 FPS | 固定镜头短窗口 |
| 377 帧 | 38.0–51.5 s | 7.3–9.9 FPS | 不同运行负载有波动 |
| 1503 帧 | 169.0–288.5 s | 5.2–8.9 FPS | 长片更接近持续速度 |

1503 帧中有一次几何不足较多的运行耗时 401.2 s（3.7 FPS），不能把它当作稳定上限，但说明失败候选和复杂画面也可能增加耗时。按长片常见的 5–9 FPS 估算，90 分钟、25 FPS 源视频约需 4.2–7.5 小时，30 FPS 约需 5.0–9.0 小时。

### 4.2 手动固定标定

手动模式只在参考帧上根据 4 对以上参考点求一次单应矩阵，并做点集、矩阵和可靠区域校验；保存后整段复用同一映射。当前 manifest 没有把这次单次计算单独计时，因为它相对于视频阶段很小。实际耗时主要是暂停视频、点选参考点、预览首中末帧和人工确认。

手动固定标定适合机位、焦距和裁切不变的片段。它不会因为逐帧白线识别失败而增加视频处理时间，也不会自动适应相机运动。

## 5. 足球追踪

### 5.1 当前默认切片流水线

`football_v11n_tile` 对每个源帧执行重叠 640 切片检测，合并重复框，再对全部候选做分窗时序束搜索。足球结果 manifest 的耗时包含模型初始化、视频解码、切片推理、候选保存、时序筛选和 JSON 写盘。

历史运行批量补跑共覆盖 4543 帧，累计墙上耗时 1981.5 s，整体吞吐约 **2.29 FPS（436 ms/帧）**。单个运行范围为 1.80–2.58 FPS；短窗口会受到启动开销影响，长片运行约 2.2–2.4 FPS。

按 2.3 FPS 粗略外推，90 分钟、25 FPS 源视频约需 16.3 小时，30 FPS 约需 19.6 小时。这是当前 CPU 切片模式的离线成本，不代表足球检测本身无法优化。

### 5.2 全图与切片的对照

早期同一台机器上的 125 帧模型基准为：

| 方式 | 125 帧耗时 | 吞吐 | 每帧耗时 |
|---|---:|---:|---:|
| YOLO11n 全图 1280 | 9.0–11.8 s | 10.6–13.9 FPS | 72–94 ms |
| YOLO11n 640 切片 | 32.3–35.5 s | 3.5–3.9 FPS | 258–284 ms |

这是检测基准，不完全等同于应用流水线；应用的默认切片结果还包含候选落盘和时序筛选，所以历史 manifest 的整体吞吐约 2.3 FPS。切片提高了远端小球的像素占比，但需要在一帧中运行多个窗口，成本约为全图的 3–4 倍。

时序筛选本身是 CPU 轻量阶段，当前没有独立计时字段；从代码结构看，足球耗时的主要部分仍是 YOLO 切片推理。它使用未来帧选择路径，因此是离线复核流程，不是零延迟实时追踪。

## 6. 三阶段合计示例

以同一段 1503 帧、25 FPS 的 `barca_girona_85m00s` 运行作为示例：

| 阶段 | 墙上耗时 |
|---|---:|
| 人物追踪（1920） | 275.2 s |
| 逐帧白线标定 | 239.3 s |
| 足球追踪（640 切片） | 665.2 s |
| 合计 | **1179.8 s（约 19.7 分钟）** |

这段素材本身约 60.1 秒，三阶段串行处理约为源视频时长的 19.6 倍。由于三个阶段会分别解码视频，并且这里的运行不是同一时刻的一次性流水线，合计用于排队和容量估算，不应当当作精确端到端基准。

## 7. 优化优先级

1. **足球先提供全图 1280 选项**：当前代码已有全图模型入口，可用于快速预览；切片用于远端小球复核。
2. **人物按目的选择输入尺寸**：日常粗看可用 1280，精度复核再用 1920；不要默认 CPU 全片使用 1920。
3. **固定镜头优先手动标定**：避免为不需要的片段执行逐帧白线阶段。
4. **不要用稠密光流做全场补偿**：早期实测约 555.7 ms/帧，远慢于当前白线方案；固定机位也不需要。
5. **后续再评估 DirectML 或 GPU**：早期 YOLOv8n 的 DirectML 单帧推理约 11.8 ms，但只测了 ONNX 会话，不包含完整 Ultralytics 后处理，不能直接等同于当前应用 FPS。

> **2026-10-22 更新**：GPU 推理已接入，见 [22 GPU 推理与设备切换](22-GPU推理与设备切换.md) 与 [CPU 与 GPU 实测对比](bench/device_compare.md)。本机（RTX 4060）实测单帧人物检测由 160.2 ms 降至 14.1 ms，但端到端人物阶段只由 3.76 提升到 8.96 FPS（2.38×）——推理提速后瓶颈转移到 `teams.py` 的球衣特征提取等 CPU 环节，且逐帧白线阶段不含神经网络、不受 GPU 影响。本文其余 CPU 基线数字仍然有效，但与 GPU 结果不可直接互比。

## 8. 可复用性能测试

性能组件位于 `src/footballer_analyzer/performance.py`，三条实际流水线都可以通过可选的 `PerformanceRecorder` 上报耗时。推荐用统一 CLI 重新执行阶段，避免把历史运行的磁盘耗时误当成当前代码速度：

```powershell
# 使用固定的 125 帧协议执行三阶段；每次都会建立新的 benchmark 目录
& .\.venv\Scripts\python.exe -m footballer_analyzer benchmark `
  --config configs/performance_benchmark.yaml `
  --stages tracking pitch ball

# 优化前后各跑一次；正式测试前先做一轮预热，连续测三轮取总工作量 FPS
& .\.venv\Scripts\python.exe -m footballer_analyzer benchmark `
  --config configs/performance_benchmark.yaml `
  --repeat 3 --warmup 1 --output-root outputs/bench

# 与旧 result.json 比较，输出每阶段 speedup（大于 1 表示更快）
& .\.venv\Scripts\python.exe -m footballer_analyzer benchmark `
  --config configs/performance_benchmark.yaml `
  --repeat 3 --warmup 1 `
  --baseline outputs/bench/benchmark_.../result.json
```

`--stages` 可单独选择 `tracking`、`pitch` 或 `ball`；`--start-frame` 和 `--end-frame` 可覆盖配置中的左闭右开区间。每轮都会实际解码视频、运行模型并写入独立目录，结果保存在 `result.json`，包含输入视频和权重摘要、代码源码摘要、环境信息、每轮记录、总 FPS、毫秒/帧和基线倍速。预热轮会执行但不进入汇总。比较基线要求素材、帧区间、配置、模型和预热协议完全一致。

如果只在 Python 测试中测一个已有阶段，可直接传入记录器：

```python
from footballer_analyzer.performance import PerformanceRecorder
from footballer_analyzer.white_line_pipeline import calibrate_run

recorder = PerformanceRecorder()
calibrate_run(run_dir, performance=recorder)
recorder.write_json("outputs/bench/manual.json")
```

该组件记录的是墙上耗时，包含对应阶段的解码、推理、筛选和产物写入；它不会给出精度结论，也不会自动把不同硬件或不同测试协议的结果视为可比。

计时沿用当前实际流水线边界：人物包含模型加载、球衣预采样和逐帧输出；白线从解码循环开始，到汇总统计前结束，包含掩膜写入，但不包含标定器构造和最终 JSON/YAML 发布；足球从模型加载前开始，到最终清单更新前结束，包含候选筛选和帧结果写入。Python 进程启动、统一测试入口准备输入、浏览器及报告都不在这些计时中。该协议标识为 `timing_version: 1`，将来改变计时边界需更换版本。

抽帧时 `fps` 表示实际处理帧吞吐，`source_frames` 保存原始区间长度，`realtime_factor` 按源区间时长计算，避免把抽帧结果误认为逐帧检测速度。足球和白线仍逐源帧执行。单独测白线或足球不会隐式执行人物检测；`pitch` 只测十一人制自动标定，手动点选耗时不属于此项。

记录器还支持给将来的子步骤计时，无需编写新的汇总脚本：

```python
with recorder.stage("candidate_filter", frames=len(records), source_fps=25):
    selected = select_candidates(records)
```

统一基准当前仍按完整阶段汇总。短片的模型加载开销较高，应在空闲机器上使用同样的预热次数和足够长的区间；不要把不同协议的短测速度当作优化收益。新增测试已覆盖公式、预热排除、独立运行、基线拒绝及失败状态。25 帧真实素材用于 CLI 连通性检查，未据此更新前面的历史性能结论。

- 人物阶段：查看对应运行的 `outputs/run_*/manifest.json`，字段为 `processed_frames` 与 `elapsed_s`。
- 逐帧标定：查看 `outputs/run_*/calibrations/lines_*/summary.json`。
- 足球阶段：查看 `outputs/run_*/balls/ball_*/manifest.json`；批量补跑汇总为 `outputs/ball-batch/football_v11n_tile.json`。
- 单帧检测和早期模型对照脚本为 `scripts/bench_cpu.py`、`scripts/bench_pipeline.py` 和 `scripts/bench_ball.py`；阶段优化应使用上面的统一 `benchmark` 命令。

这些数字没有包含浏览器绘制、人工复核和报告导出的完整交互时间，也没有用 GPU 重测。候选数量、有效标定帧数和足球选中帧数是结果覆盖指标，不是速度或准确率。
